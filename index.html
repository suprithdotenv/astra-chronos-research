ASTRA CHRONOS: AI-powered counter-UAS interception simulator

ASTRA CHRONOS is a software-only simulation and decision-support platform. It models the path from simulated radar telemetry to behaviour assessment, threat scoring, trajectory prediction and virtual interception, and presents the result in a 3D radar-style command console.

Telemetry→Behaviour→Threat score→GRU prediction→Virtual interceptor→3D console
9Research modules
5Behaviour classes
3Predictors compared
4API endpoints

Objectives

  • Real-time simulation with a stable tick-based loop.
  • Predictive AI that estimates future trajectory, not only current position.
  • Interpretable threat prioritization across scenarios.
  • Model validation by measuring prediction error and interception outcomes.
  • Graceful fallback to a deterministic kinematic predictor if the trained model is unavailable.
  • Coherent visualization of tracks, predicted paths, threat history, zones and interceptor state.
Simulation safety boundary: the project is explicitly virtual. It is not a real-world interception or weapon-control system.

Module 1

Problem understanding

Counter-UAS (C-UAS) covers methods for detecting, monitoring, assessing and responding to potential drone threats. This project focuses on the software simulation and decision-support side.

Four related challenges

ChallengeQuestion
Situational awarenessWhere are the drones and how are they moving now?
Behaviour understandingIs a drone moving normally, hovering, loitering or evasive?
Future movement predictionWhere might it be a short time from now?
Decision supportHow are observations, uncertainty and outcomes presented to an operator?

These are distinct problems: a system can track accurately while predicting poorly.

Why it is difficult

Official guidance cites small size, unpredictable movement and confusion with birds. For this research the main issues are noisy or missing telemetry, changing movement, prediction uncertainty when behaviour changes, the fact that movement alone does not prove hostile intent, and real-time operation without an unresponsive interface. These are research questions, not solved claims.

Success looks like

  • Reliable runs across scenarios.
  • Classification evaluated against known simulated labels.
  • Threat scores that respond consistently to controlled scenario changes.
  • Predictions compared with true trajectories and simpler baselines.
  • A dashboard that matches backend state, and reproducible mission outcomes.

Guiding principle: every important capability is evaluated rather than judged by appearance.

Module 2

Drone simulation and telemetry

A simulator maintains a virtual drone state and advances it over time. This gives repeatable scenarios and known ground truth at every step. Success in simulation does not automatically transfer to real drones.

Telemetry (illustrative)

VariableExampleMeaning
Time2.0 sWhen the observation occurred
Position X, Y, Z12, 8, 15 mLocation in the chosen coordinate system
Velocity3 m/sSpeed and direction of change of position
Heading45°Facing direction, not always the direction of travel

Acceleration (m/s²) describes how velocity changes. A trajectory is the sequence of positions over time; the observed part is recorded, the predicted part is estimated and compared with simulator ground truth.

Flight behaviours (simplified categories, not real intent)

BehaviourSimulated as
Normal flightSmooth changes in position
HoveringSmall variations around one location
LoiteringRepeated or curved paths in an area
Evasive movementIrregular turns or speed changes
Fast approachRapid movement with increasing proximity to a target area

Noise, time and leakage

  • Ground truth (exact simulator state) is kept separate from observed telemetry (possibly noisy, missing or delayed).
  • Simulation time and wall-clock time differ. Consistent time steps matter, for example 0.05 s (20 updates per second) as an illustrative interval.
  • Data leakage: split train and test by whole trajectories or scenario configurations, not individual time steps. Results then show simulated generalisation only.

Simulator options (none selected)

A: mathematical motion simulator (simple, controllable, may omit real dynamics). B: physics-based robotics simulator (richer, more setup). C: flight simulator (depends on interfaces and data access).

Module 3

Behaviour classification

Classification identifies how a drone moves from its telemetry. The label supports the console display, gives context to threat assessment and feeds the prediction module. It describes movement, not intent.

ApproachHow it worksTrade-off
Rule-basedConditions such as low speed for hoveringSimple, rules need careful design
Machine learningLearns from labelled movement dataNeeds representative training data
HybridCombines rules and learned patternsFlexible, more complex

Implementation approach

  1. Collect position, velocity and history each time step.
  2. Compute features: speed, change in speed, turning rate, position change over time.
  3. Apply rules based on sustained patterns that tolerate noise, for example sustained near-zero speed for hovering and repeated circular motion for loitering.
  4. Return the label with confidence or evidence to the React console.

The plan starts with rules as a baseline, then tests whether machine learning improves it, using held-out simulated trajectories with precision, recall and a confusion matrix.

Module 4

Threat assessment

Each simulated drone receives a priority score from its movement and scenario context. Classification says how it moves; the score says how much attention it may need.

Position, speed, direction, behaviour, zones→Distance to zone, direction, time to reach→Scoring engine→Score, category, reasons

Illustrative weighted score

score = round(100 * (0.40 * zone_proximity
                   + 0.35 * approach_factor
                   + 0.25 * speed_factor))

Inputs are normalized from 0 to 1. The weights are starting values, not validated constants. Provisional bands: 0 to 29 low, 30 to 59 medium, 60 to 100 high. The score is a simulated priority, not a probability of hostility.

ApproachTrade-off
Rule-basedEasy to explain, may be rigid
Weighted scoring (starting point)Transparent, weights need calibration
Machine learningOnly if meaningful ground-truth labels exist

Tests: score rises on approach to a zone, accounts for direction and not distance alone, stays stable under noisy telemetry, can be explained in the console, and handles edge cases such as a fast drone moving away from a zone.

Module 5

Trajectory prediction

Primary research focus: can AI predict a drone’s future position more accurately than simpler motion models?

ModelHow it predicts
Constant velocityContinues the current velocity
Kalman filterEstimates motion while accounting for measurement noise
GRU neural networkLearns patterns from sequences of past movement

GRU training plan

  1. Generate many simulated trajectories.
  2. Split each into past movement (input) and future movement (target).
  3. Train the GRU to predict future positions.
  4. Test on entirely separate trajectories.
  5. Compare errors with the baseline models.

Metrics: Average Displacement Error (ADE), the mean distance between predicted and actual positions, and Final Displacement Error (FDE), the distance at the final prediction time. The aim is lower error, especially during turns and changing movement. The complex model must be shown to improve on the baselines, not assumed to.

Module 6

Virtual interception simulation

A virtual interceptor responds to the target’s predicted movement, entirely inside the software environment. The target follows a predefined scenario; the interceptor follows a selected test policy. Nothing controls real aircraft or weapons.

Target state and predicted path→Update interceptor under policy and constraints→Check success conditions and limits→Publish tracks and metrics
  • Scripted simulation: predefined path, used as a baseline.
  • Rule-based simulation: explicit movement rules and constraints.
  • Prediction-assisted simulation: predicted target positions feed the test policy.

Evaluation: scenario success rate, completion time, constraint violations, and prediction impact against a baseline that does not use predictions. Success conditions and movement constraints are defined before testing. The key question: does improved prediction lead to measurable improvement in simulated outcomes?

Module 7

Command console and visualization

A React-based 3D dashboard monitors the simulation in real time.

  • 3D view: drone positions, movement trails, predicted paths and virtual zones.
  • Drone panel: speed, classified behaviour, threat score and predicted trajectory.
  • Controls and history: scenario selection, start, pause and reset, threat-score history and interceptor status.

Data flow: the Python backend updates states and predictions, a FastAPI endpoint sends the data to React, React updates the scene and panels, and user commands return to the backend. Candidate technologies: React with Vite, Three.js or React Three Fiber, charts, and FastAPI. The 3D library and update method are not finalized.

Module 8

Data, datasets and evaluation

  1. Generate simulated flights across scenarios.
  2. Record positions, velocities, timestamps, behaviour labels and ground truth.
  3. Clean data and split whole trajectories into training, validation and test sets.
  4. Evaluate on unseen scenarios.
DataPurpose
Position and velocityTrain trajectory prediction
Behaviour labelsTrain and evaluate classification
True future positionsCheck prediction accuracy
Noise-affected observationsTest robustness
Scenario labelsCompare performance across conditions

Metrics: ADE and FDE for prediction; precision, recall and confusion matrix for classification; threat scores checked against predefined simulation priorities; robustness repeated with noisy or missing observations. Good results on simulated data show performance in those scenarios, not necessarily real-world performance.

Run flow

Start in React, request to FastAPI, simulation initialized, engine advances each tick, AI modules analyse telemetry, FastAPI returns state and results, React updates position, path, label and score. Pause and reset follow the same pattern.

Decisions

  • The backend owns simulation state; the frontend displays it.
  • Each update follows a defined time step.
  • AI modules are independent and testable separately.
  • Without a trained GRU checkpoint, a baseline predictor takes over.
  • Request and response structures are agreed as clear API contracts.
Design

Data flow

Scenario configuration→Simulation engine→Telemetry processing→Behaviour, score, prediction→FastAPI response→React console

Example state (illustrative)

{
  "drone_id": "drone_01",
  "timestamp": 12.0,
  "position": [10.0, 5.0, 8.0],
  "velocity": [2.0, 0.5, 0.0],
  "behaviour": "normal_flight",
  "threat_score": 25,
  "predicted_positions": [[12.0, 5.5, 8.0], [14.0, 6.0, 8.0]]
}

Positions are in metres, velocities in metres per second, timestamps in simulation seconds. Two streams are kept apart: ground truth for evaluation, and observed telemetry, possibly noisy, supplied to the AI. React sends commands (initialize, advance one tick, pause, reset) to FastAPI, which calls the modules and returns JSON. The MVP uses ordinary HTTP; WebSockets are considered only if continuous updates become inefficient.

  1. Simulation engine: position, velocity and telemetry each tick.
  2. Analysis modules: behaviour, transparent threat scoring, baseline predictor.
  3. FastAPI backend connecting them through consistent endpoints.
  4. React frontend: drone, trail, predicted path, behaviour, score, controls.
  5. Integration and testing.

AI performance is measured with ADE, FDE, precision, recall and robustness to noise or missing observations, always against simpler baselines.

Expansion phases

  1. Working MVP: one drone, baseline prediction, simple scoring, API and dashboard.
  2. Data and AI validation: generate datasets, train candidate models, compare on held-out scenarios.
  3. Complete demonstrator: more scenarios, richer visualization, model fallback and interceptor-state visualization.

The MVP is ready when a user can start a scenario, observe the drone, see its behaviour and threat score, view predicted positions, and reset without errors.
